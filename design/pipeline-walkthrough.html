How the UI and backend agree

PreparationConvex Workflow journals preparation steps; the app stores queued → resolving → downloading → separating (music only) → transcribing → review. The UI shows the actual stage, without an invented percentage or ETA.
Word list changesA local “settings changed” notice appears. The old mix remains labeled as the previous version. Clicking Render requests a new cache key; stems and timestamps stay reusable.
RenderConvex stores queued → rendering → ready, or failed. The worker edits samples and encodes one MP3. Duplicate requests reuse the same in-flight job or finished file.
PlaybackPlay, pause, seek, and “inside an edit” are local player states. The word silence is already in the file; the browser does not have to send a perfectly timed mute command.
FailureAccess denial stops before transcription. Preparation and rendering can be retried separately. Attempt numbers prevent old callbacks from overwriting a newer attempt. Original audio is never silently substituted for a filtered mix.
Cache boundaryPreparation is scoped to account + source + processing version. The saved original is pinned. Render keys include recording hash, selected words, edit intervals, gain, and processing version. Current caches are per account.

Current scope: Audius tracks and RSS podcast episodes; exact recognized-word filtering; music ≤30 minutes / 24 MiB; longer podcast episodes use a preview of the first 30 minutes (incoming file ≤512 MiB). Podcasts mute the whole recording at each chosen word, including any background bed. Topic classification, section skipping, automatic subscriptions, refresh-to-new-edition controls and native background playback are outside this new pipeline. Vocal leakage and transcription mistakes need listening review.
